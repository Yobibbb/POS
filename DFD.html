The CartAlogue POS is the sole central process. Three external entities define its boundary.

The Smart Basket (ESP32) transmits barcode scan events and session data into the POS. The POS returns pairing acknowledgment and session confirmation to activate the ESP32's scanner and audio-visual feedback.

The Mobile Application sends pairing triggers and checkout requests. The POS delivers live itemized totals, checkout codes, and digital receipts back to the shopper's phone.

The Database supplies the product catalog and session records for lookup. Upon payment, the POS writes finalized transaction history and updated session state back to the Database for long-term storage.

Level 1 decomposes the CartAlogue POS into five numbered processes and four internal data stores. External entities remain identical to Level 0. No two processes communicate directly — all data exchanges pass through a data store, keeping the design traceable and consistent with Yourdon-DeMarco DFD conventions.

The Mobile App sends its device ID and the ESP32 sends its basket signal simultaneously to process 1.1. Process 1.2 checks the Session Store (D2) to confirm the basket is not already paired. Process 1.3 writes a new session record to D2. Process 1.4 broadcasts the pairing acknowledgment to the ESP32 (activating its barcode scanner) and sends the session confirmation to the Mobile App.

Each ESP32 scan sends a barcode string with a basket ID to process 2.1. Process 2.2 resolves the barcode against D1 (Product Catalog) to get the name and unit price. Process 2.3 merges the product into the active session in D2. Process 2.4 recalculates the running total. Process 2.5 immediately pushes the updated item list and total to the Mobile Application in real time.

When the shopper is done, the Mobile App sends a checkout request. Process 3.2 retrieves the full session summary from D2. Process 3.3 generates a unique alphanumeric checkout code. Process 3.4 freezes the item snapshot and total into the Checkout Codes store (D4). Process 3.5 returns the code as QR data to the Mobile App for the shopper to present at the cashier counter.

The cashier scans or types the checkout code at the POS counter. Process 4.1 retrieves the pending record from D4. Process 4.2 cross-references session details from D2 and displays the full transaction. Process 4.3 computes change after the cashier enters the amount received. Process 4.4 generates a unique receipt number. Process 4.5 writes the completed transaction to D3 (Transaction History) and to the external Database. Process 4.6 marks the checkout code in D4 as completed to prevent reuse.

After each completed payment, process 5.1 immediately saves the transaction to local D3 (Transaction History) with synced = false — keeping the POS fully operational offline. Process 5.2 continuously monitors network connectivity. When the internet is restored, it triggers process 5.3 to retrieve all unsynced records from D3 in a batch. Process 5.4 pushes the batch to the external Database (Firebase in online mode) and waits for a write confirmation. Process 5.5 then updates each record in D3 to synced = true to prevent duplicate uploads.
